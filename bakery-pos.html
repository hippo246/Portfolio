Bakery POS

Full-stack bakery point-of-sale and management system — React, Vite, Tailwind CSS, Recharts

← Back to Portfolio

Project Overview

BakeryPOS is a full-featured point-of-sale and operations management system built specifically for bakeries and cafés with React, Vite, and Tailwind CSS. It goes well beyond a basic POS — featuring a per-seat course ordering system for multi-course meals, token management with a customer-facing TV display for order pickup, a drag-and-drop floor plan editor for table management, a waiter service terminal for staff order management, QR-code self-ordering for customers, kitchen display screens (KDS) for order preparation, advanced reporting with 80+ report types, and a comprehensive menu designer with raw ingredients tracking, cost calculation, and stock management. The system also includes on-device AI capabilities using @xenova/transformers for local inference.

The system addresses bakery-specific pain points: course-based ordering complexity (appetizers, mains, desserts served in sequence), customer pickup queue management (customers waiting for token numbers), inefficient table seating during busy periods, lack of real-time kitchen visibility, manual ingredient tracking leading to food waste, and inability to predict stock-outs before they happen.

Built with AI-assisted development using Kiro, Devin (formerly Windsurf), Antigravity, Trae, and Claude. My contribution involved defining all operational workflows by studying real bakery operations, designing the data model and navigation structure for 15+ modules, creating the per-seat course ordering system, building the token TV display for customer-facing status, implementing the kitchen order ticket and KDS systems, testing every module across different scenarios, and iterating on the interface based on usability feedback.

Problem Statement

Bakeries and cafés have unique operational challenges that generic POS systems don't address:

  • Course-based ordering complexity: Unlike quick-service restaurants, bakeries with café seating serve courses (appetizers, mains, desserts) in sequence, requiring per-seat ordering and staged firing to the kitchen
  • Pickup queue chaos: Customers waiting for takeout orders crowd the counter asking "is my order ready?" without knowing their token number or status
  • Inefficient seating: Manual table tracking with basic tools causes poor table turnover during peak breakfast and lunch rushes
  • Kitchen visibility gaps: Kitchen staff don't see order priority or elapsed time, leading to first-in-first-out processing regardless of urgency
  • Ingredient waste: Manual ingredient tracking is error-prone, leading to over-preparation, food waste, and inconsistent food costs
  • Stock-out surprises: No predictive insights for ingredient shortages, leading to last-minute panic ordering and disappointed customers

BakeryPOS was built to address these bakery-specific needs with course ordering, token management with TV display, per-seat tracking, kitchen priority systems, ingredient-level inventory, and predictive stock-out alerts.

Solution Approach

The solution uses a modular architecture with specialized modules for bakery operations. Key architectural decisions:

  • Per-seat course ordering: Data model designed around seats rather than just orders, with course sequencing (Course 1/2/3) and staged firing to kitchen based on customer progress
  • Token TV display: Fullscreen customer-facing display showing order status (Being Prepared vs Ready to Collect) with large token numbers and scrolling ticker, designed for TV mounting in pickup area
  • Floor plan editor: Drag-and-drop table layout editor with sections (Main, Outside, The Bar, Open), table status colors, and per-table bill panel with seat-level detail
  • Kitchen dual-display: Both Kitchen Order Tickets (KOT) with printer lanes for traditional kitchens and Kitchen Display System (KDS) with digital order cards for modern kitchens
  • Ingredient-level inventory: Menu items linked to raw ingredients with automatic stock deduction, cost calculation, and margin tracking per item
  • On-device AI: @xenova/transformers integration for local AI inference (no cloud dependencies) for predictive analytics and pattern recognition
  • Deferred integrations: Cloud storage providers (Supabase, AWS S3, Azure, WebDAV) and payment gateway (Razorpay) are architected but deferred for client deployment

Development Process

The project followed a structured development process with AI-assisted coding:

  • Requirements gathering: Studied real bakery operations across different types (standalone bakery, bakery with café seating, quick-service bakery), interviewed bakery owners, bakers, and counter staff to understand pain points, documented workflows for ordering, course service, token management, kitchen operations, and seating
  • Architecture design: Designed per-seat data model for course ordering, planned token TV display architecture for customer-facing status, designed dual kitchen display (KOT for traditional, KDS for modern), planned ingredient-level inventory system, integrated @xenova/transformers for on-device AI, and decided which cloud integrations to defer for client deployment
  • Incremental implementation: Built Standard POS first (basic ordering, cart, checkout), then Advanced POS with per-seat course ordering, then token management with TV display, then tables and floor plan editor, then kitchen systems (KOT and KDS), then waiter service terminal, then QR self-ordering, then menu designer with ingredients, then dashboard and reports, and finally polished UI and UX
  • AI-assisted development: Used Kiro for generating React components and refactoring code, Devin (formerly Windsurf) for debugging state synchronization issues between token board and TV display, Antigravity for architectural decisions and data model design, Trae for building UI components with Tailwind CSS, and Claude for documentation, problem-solving, and edge case handling
  • Testing and iteration: Tested each module with realistic bakery scenarios, simulated course-based ordering with multiple seats, tested token TV display on actual TV, tested floor plan drag-and-drop on different devices, validated kitchen order firing sequences, gathered feedback from bakery industry professionals, and iterated on the interface based on usability testing

Challenges & Lessons Learned

  • Per-seat course ordering complexity: Per-seat course ordering adds significant complexity — items need to be associated with a seat and a course, then fired to the kitchen in sequence rather than all at once — required designing a complex data model and careful state management, learned that course-based workflows need clear rules for when courses fire and how the kitchen receives staged orders
  • Token TV display synchronization: The token TV display runs as a separate fullscreen mode with its own state, needing to stay in sync with the main token board without refreshing, required implementing a shared state mechanism with real-time updates, learned that fullscreen displays need to handle window focus events and graceful exit
  • Floor plan persistence and sync: Floor plan layout editing — storing table positions, sections, and status in a way that persists across sessions and syncs with live order state — required careful data structure design and conflict resolution, learned that UI state (layout) must be separated from operational state (orders) while maintaining linkage
  • QR ordering context isolation: QR self-ordering runs on the customer's device with no staff login, so it needs a completely different UI context while sharing the same order data model, required designing a guest session system that isolates customer view from staff view, learned that guest sessions need to be stateless from server perspective but stateful on client for smooth UX
  • Ingredient-level inventory integration: Linking menu items to raw ingredients with automatic stock deduction required careful transaction design to handle partial usage, returns, and stock corrections, learned that inventory transactions need complete audit trails and rollback capability
  • On-device AI limitations: Using @xenova/transformers for on-device AI inference revealed model size and performance limitations on lower-end devices, learned to provide fallback to server-side AI or rule-based systems when on-device inference is too slow
  • Dual kitchen display complexity: Supporting both Kitchen Order Tickets (KOT) for traditional kitchens and Kitchen Display System (KDS) for modern kitchens required designing two different interfaces for the same underlying data, learned that feature flags and configuration are essential for supporting different operational models
